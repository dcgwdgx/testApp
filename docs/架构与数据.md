# 架构与数据

## 页面结构

| 页面 | 文件 | 作用 |
| --- | --- | --- |
| 首页 | `app/index.tsx` | 展示产品价值、代表设计、免费次数和入口 |
| 生成页 | `app/generate.tsx` | 选择图片、风格和强度，校验免费次数或积分并发起生成 |
| 结果页 | `app/result.tsx` | 展示生成结果并承载原图对比、保存和分享 |
| 历史页 | `app/history.tsx` | 查看、删除或清空本机最近 10 条记录 |
| 隐私页 | `app/privacy.tsx` | 展示应用内隐私政策 |

`app/_layout.tsx` 负责路由栈、统一标题栏样式和 `app_open` 事件记录。

## 核心模块

| 模块 | 文件 | 作用 |
| --- | --- | --- |
| AI 接口 | `lib/api.ts` | 构造请求、设置超时、重试并返回 Base64 图片 |
| 环境配置 | `lib/config.ts` | 从 Expo 配置读取 Ark API 密钥 |
| 风格定义 | `lib/styles.ts` | 定义 24 个设计、分类、展示文本和生成提示词 |
| 内购 | `lib/purchases.ts` | 拉取商品、发起购买、增加或扣减积分、交易去重 |
| 历史 | `lib/history.ts` | 在 AsyncStorage 中保存最多 10 条生成记录 |
| 分析 | `lib/analytics.ts` | 把最多 500 条产品事件写入本机队列 |
| 运行时缓存 | `lib/cache.ts`、`lib/photoCache.ts` | 在页面跳转间传递当前图片和生成结果 |

## 生成流程

1. 用户通过系统图片选择器选取一张图片。
2. 图片裁剪为 1:1，并压缩为最大 1024×1024、质量 0.8 的 JPEG。
3. 用户从 24 个设计中选择一个，并设置风格强度。
4. 应用检查 1 次免费机会或本机剩余积分。
5. 客户端直接把 Base64 图片、风格提示词和强度发送到火山引擎 Ark API。
6. 接口使用 `doubao-seedream-5-0-lite-260128` 模型，要求 2K、Base64 返回和关闭平台水印。
7. 请求超时为 120 秒，失败最多重试 2 次。
8. 成功后结果保存在运行时缓存和本机历史中，然后扣减免费次数或积分。
9. 用户可以查看结果、原图、滑动对比、保存或分享。

## 本地数据

| 数据 | 存储位置 | 保留规则 |
| --- | --- | --- |
| 免费次数 | AsyncStorage：`@free_used` | 当前设备长期保存，清除应用数据后丢失 |
| 剩余积分 | AsyncStorage：`@remaining_credits` | 当前设备长期保存，不跨设备同步 |
| 已处理交易 | AsyncStorage：`@processed_purchases` | 最多保留最近 200 个交易标识 |
| 生成历史 | AsyncStorage：`@pet_portrait_history` | 最多 10 条，包含原图和结果的 Base64 数据 |
| 分析事件 | AsyncStorage：`@analytics_queue_v1` | 最多 500 条，目前不上传 |
| 当前图片与结果 | 内存变量 | 应用进程结束后清空 |

生成历史包含较大的 Base64 图片，因此限制为 10 条以降低 AsyncStorage 容量风险。

## 第三方服务与数据流向

- 火山引擎：接收用户上传的宠物照片、生成提示词和强度参数，用于生成图片。
- Apple App Store 或 Google Play：处理商品信息和支付交易。
- Expo/EAS：用于构建和提交应用。
- GitHub Actions：执行自动构建和发布流程。

项目没有自建业务服务器、用户账号系统或远程数据库。应用不会主动收集姓名、邮箱、精确位置或广告标识符；但宠物照片会发送到火山引擎处理，这一点必须与隐私政策和商店数据安全声明保持一致。

## 安全与可靠性边界

### 客户端密钥

`ARK_API_KEY` 被写入 Expo `extra`，最终客户端可以读取，因此它不是安全的长期密钥存储方式。正式扩大流量前，应由受控后端持有密钥，并增加身份校验、额度限制、滥用防护和日志脱敏。

### 购买校验

当前积分发放依赖客户端交易回调和本机交易标识去重，没有服务端收据验证，也没有账号级积分账本。卸载、换机、篡改本地数据或异常交易恢复可能造成积分不一致。扩大付费规模前，应增加服务端收据校验和幂等积分发放。

### 分析能力

`trackEvent` 只把事件写入本机队列，当前没有 PostHog、Firebase、Amplitude 或自建上报端点。因此代码中虽然有漏斗事件名称，但后台还看不到真实转化数据。

### 错误恢复

生成接口具备超时、取消和重试；历史保存失败会静默忽略，因为它不是关键链路。支付失败会记录本机事件并提示用户，但没有远程告警。

## 优先技术改进

1. 把 AI 调用迁移到受控后端，停止向客户端分发 Ark 密钥。
2. 增加服务端收据校验、交易幂等和跨设备积分同步。
3. 接入真正的远程漏斗分析和错误监控。
4. 增加单元测试、关键页面集成测试和至少一条生成流程端到端测试。
5. 给历史图片改用文件系统存储，AsyncStorage 只保存索引和元数据。
